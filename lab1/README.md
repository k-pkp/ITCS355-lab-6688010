# ITCS355 — Predicting machine failure within 7 days

> with no path reaching outside. The other labs sit beside it and each carries its own copy

Predicting machine failure within 7 days from sensor readings. The model is not the point;
whether a stranger can reproduce it is.

---

## Reproduce

```bash
make reproduce
```

expected test_roc_auc: 0.848 ± 0.005

Runtime: about 40 seconds of training on 4 cores, plus 3–4 minutes for the image build on a
cold Docker cache. No cloud account or credentials are needed for this command — that is
deliberate, and it is why a grader can run it.

**Where the tolerance comes from.** At the pinned seed the run is deterministic: two host
runs and one container run all produced `test_roc_auc = 0.8482378548603715`, identical to
the last digit. The ±0.005 is headroom for a different CPU and a different BLAS build, not
for wandering. It is deliberately *smaller* than the seed-to-seed spread — five seeds on the
same configuration give 0.8384 to 0.8667, sd 0.0106 — because that spread measures a
different thing: a different split of machines, not a different answer to the same question.
Quoting the wider number as the tolerance would be padding.

## The problem

240 machines, 25 readings each, 6 sensor features, binary target `failed_within_7d` with a
positive rate of 11.7%.

Machines have persistent characteristics — a hot-running machine reads hot in every row. So
the train/validation/test split is **grouped by `machine_id`**: every reading from one
machine lands in exactly one partition. Splitting row-wise instead lets the model memorise
the machine and reports a validation score that will never survive production.
`tests/test_data.py::test_no_machine_leaks_across_splits` asserts this property holds, and
Lab 4's CI pipeline runs it as a gate.

The data is generated by `scripts/make_dataset.py` and versioned with DVC; the remote is
`${BLOB_URI}/dvc`. Bringing your own dataset is allowed: replace the generator, update the
schema in `src/data.py`, and keep every test passing.

## Reproducibility trade-off

Three things pin this build: hashed dependencies, a digest-pinned base image, and controlled
seeds. Under real time pressure, **drop the hashes first.**

Versions are still pinned without them, so the build changes only if a maintainer
republishes an artifact under an existing version — rare, and loud when it happens. What
breaks is the guarantee against a *substituted* wheel: a supply-chain swap becomes invisible
instead of a build failure. That is a security regression, not a reproducibility one.

Dropping the base-image digest is worse: `python:3.11-slim` moves weekly and takes glibc and
OpenSSL with it. Dropping seeds is worst — the number changes on the same machine, on the
same day, and nothing tells you.

## Which incident each data contract test would have caught

Named because Lab 4 asks for the incident, not the assertion.

| Test | The incident |
|:--|:--|
| `test_schema_columns_present_and_typed` | The sensor gateway's CSV export gains a column after a firmware update, or `machine_id` starts arriving as a zero-padded string. Training then silently one-hot encodes an identifier, or drops a feature, and the metric barely moves. |
| `test_no_nulls_in_required_columns` | A polling failure on one sensor leaves `vibration_mm_s` empty for a subset of machines. Nulls become imputed means, the most important feature (41% importance) turns into a constant for those rows, and they all score the same. |
| `test_features_within_plausible_ranges` | A recalibration ships and `temp_c` arrives 6 °C high across the fleet — the exact incident reconstructed in `reports/lab4-drift.md`. Ranges catch the gross version of it at ingest, a week before the drift monitor's delayed labels would. |
| `test_target_is_binary_and_not_degenerate` | The labelling job that computes `failed_within_7d` breaks and writes 0 for everything. Training succeeds, ROC AUC is undefined or 0.5, and a model that predicts "never fails" ships. |
| `test_identifier_is_unique` | An upstream join fans out and duplicates readings. Duplicates cross the train/test boundary through the group split, and the reported score becomes memorisation. |
| `test_no_machine_leaks_across_splits` | The split is changed to row-wise "because it is simpler". Validation ROC AUC jumps, everyone is pleased, and production performance does not move at all. |

## Drift threshold

**PSI ≥ 0.20**, per feature, against the reference window. Measured, not copied: PSI between
the reference and a 600-row window of *unchanged* data peaks at 0.043, and it takes a
two-sigma shift of the most important feature (PSI 3.54) before ROC AUC moves by 0.011. The
threshold sits at 4.6x the noise ceiling and far below the harm floor on purpose — the label
here arrives seven days late, so the input-side statistic is the only same-day signal, and
its job is to start an investigation, not to trigger a retrain. Full working in
[`reports/lab4-drift.md`](reports/lab4-drift.md).

## Who should be allowed to promote a model, and on what evidence

Not the person who trained it, and not automatically. In a real organisation, promotion to
production should require the sign-off of whoever carries the pager for the service — the
team that gets woken when it misbehaves — because promotion is the moment a model becomes
someone's operational burden.

The evidence they should require, all of it available before the decision: the eight lineage
fields on the registered version, so the model traces to exact code and exact data; the
evaluation gate's output, showing the margin over the incumbent and that the margin exceeds
seed noise; the canary result with its detection time; and a named rollback path that
somebody has actually executed. "The metric is higher" is not evidence, because a 0.005
improvement on this data is indistinguishable from a different random split.

CI may promote to **staging** unattended. Nothing promotes to production unattended.

## What should trigger a retrain

| Strategy | When it is right for this system | How it fails here |
|:--|:--|:--|
| **Fixed schedule** (chosen: weekly, Sunday 02:00) | The fleet changes slowly and the label takes 7 days. A week's new data moves the training set by under 1%, which is well inside the seed noise of 0.0087 — so weekly is already more often than the data justifies, and it is chosen for operational rhythm rather than for statistical need. A pipeline that runs regularly is a pipeline that still works when you need it. | Wastes compute on retraining that changes nothing, and — worse — a schedule that always succeeds trains you to stop reading its output. It also cannot react: if the fleet genuinely changes on a Monday, the model is six days stale before anything happens. |
| **Data volume threshold** | Would suit a growing fleet: retrain when 20% more machines have accumulated a full history. Ties the work to information gained rather than to the calendar. | This fleet is 240 machines and roughly fixed, so the trigger would fire almost never, and a system whose retraining path runs once a year is a system whose retraining path is broken and nobody knows. |
| **Drift-triggered** | The instinctive answer, and the dangerous one here. | Two independent failures. First, the detector is blind to the drift most likely to happen: a fleet composition change scored PSI 0.0087, below the noise floor, while a uniform shift that did no harm scored 0.383. Retraining on the second and missing the first is exactly backwards. Second, and far worse: **a drift alert cannot distinguish a real change from a broken upstream pipeline.** The 6 °C shift in `reports/lab4-drift.md` was a recalibration bug. Retraining on it would have baked a broken calibration into the model as though it were the world, and the last good model would already have been replaced. |

**Chosen: fixed weekly schedule, with drift as an alert to a human, never as a trigger.**

The worst case for the chosen strategy is bounded and slow: the world changes on a Monday
and the model is six days stale. The worst case for the strategy not chosen is unbounded and
fast — an upstream pipeline breaks at 01:00, the drift alert fires at 01:30, the automated
retrain finishes at 02:00 on corrupted data, and the working model is gone. One of those is
recoverable by waiting. The other is recoverable only by noticing.

## Notes for the grader

**Run `make reproduce` and `make verify`; everything else is optional.** The claim above was
produced by exactly that command on 2026-09-07.

Things that will otherwise prompt an email:

* **`make` needs a Python 3.11 environment.** The lock file targets 3.11; the container
  builds one for itself, so `make reproduce` is unaffected. `make test` on a 3.14
  interpreter will not resolve the pins.
* **Managed cloud is deliberately absent.** Object storage (GCS), the container registry
  (Artifact Registry) and Cloud Monitoring are real and were exercised: the image is pushed
  and digest-pinned, `dvc push` completed, and `emit_metric` wrote a real time series. The
  Vertex AI API is not enabled on this project, so managed training, managed endpoints and
  the managed LLM were not run. Everything that depends on them — `submit_training`,
  `deploy`, `invoke`, `generate`, the Vertex `teardown` — is implemented and unexercised,
  and every report says so where it matters rather than implying otherwise.
* **Labs 2 and 3 were measured locally.** The hyperparameter study ran on local CPU priced
  at the verified `e2-standard-4` rate; the load tests ran against uvicorn and against the
  serving container with `--cpus` limits so the shapes match instances that can be bought.
  The reports label every such figure.
* **The LLM fixtures were authored, not recorded.** They specify the contract and the gate's
  pass/fail behaviour is real. Token counts in the cost report come from the course's
  recorded fixture, whose counts are provider usage fields; `make llm-record` re-records
  live. `reports/lab5-llm.md` states this in full.
* **The load-test numbers use `K6_NO_CONNECTION_REUSE=true`.** Keep-alive against a
  multi-worker uvicorn adds a flat ~40 ms delayed-ACK stall that has nothing to do with the
  service — server-side logs said 9.8 ms while the client said 51.9 ms for the same
  requests. Documented in `reports/lab3-load.md`.
* **`.dvc/config` and `cloud.env` contain provider strings.** The portability audit does not
  scan them, and that gap is the most interesting finding in
  `reports/lab5-portability.md` rather than an oversight.
* **Two bugs were found by measuring rather than by reading**, and both are fixed with the
  evidence recorded: the registered model carried `n_jobs=-1` into serving (37 ms per row,
  of which 8 ms was the forest), and containerised runs logged `git_commit=unknown` because
  the image has no `.git`.
